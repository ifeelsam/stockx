## 2026-11-26: 100k CU per payout action so a full claim batch fits the validator's intent limit
- Finding: on live devnet (validator core 2.0.5) `claim_all` of 8 cards failed with `0xA0000002` (INTENT_TOO_LARGE). `core/src/intent/limits.rs` caps a settlement stage at 1,400,000 CU (120k per committed account + each action's requested CU + 1k). We requested 200k per action: 1.72M. Earlier runs never claimed more than a few winners, and MagicSVM does not model this limit.
- Decision: request 100,000 CU per `pay_out_action` (measured use 25-32k) and keep the batch at 8; a compile-time assert guards the product. Action fee halves to 5,000 lamports per card.

## 2026-11-26: MagicBlock conformance run on devnet: what it changed
- **Deposits use two eSPL builders.** The legacy `delegateSpl` (`idempotent: false`) rejects an already-delegated balance, so every top-up failed. The shuttle builder, used for a first deposit, can merge before the rollup ATA exists and strand the amount (seen live). SDK picks by whether the eATA is delegated, then waits for the amount (not the account) before `deposit_usdc`.
- **Withdrawals use the shuttle builder** (the legacy `withdrawSpl` needs the eATA undelegated first).
- **Commit-fee reserve is topped up from the client** with `lamportsDelegatedTransferIx` when under 0.003 SOL. The 0.01 SOL from `signup` covers about 35 commits per delegation. No program change.
- **Keeper payout repair judges claims by the rollup copy.** Judging by the committed base snapshot dropped a player whose commit had not landed yet, so dropped Magic Actions were never repaired.
- **Not done:** `VaultState` is not committed periodically and has no delegated payer + `magic_fee_vault` (CLAUDE.md §3); it only commits on admin undelegate. Onboarding asks the wallet for four signatures, not at most two (§6). Apps use the fixed asia rollup rather than the router (the router agrees for every delegated account).

## 2026-11-26: Keeper stays; native cranks cannot replace it. Faucet capped before going public
- A MagicBlock crank repeats instructions whose accounts and data are fixed when scheduled (`ScheduleTaskArgs { task_id, execution_interval_millis, iterations, instructions }`, SDK 0.18.0 crates), so it cannot fetch a price. Re-sending one `push_price` is rejected after the first (timestamp must increase). The faucet is a web endpoint and the sell quote and payout repair are base-layer transactions signed with our keys. On validator 2.0 (our rollup runs 2.0.5) scheduled instructions also cannot carry signers, and they fire only while a Hydra cranker runs.
- Public faucet: at most 6 SOL drips per hour, never below 1 SOL in the funder, per-IP throttle keyed on Fly's `fly-client-ip` instead of the forgeable `x-forwarded-for`.

## 2026-11-26: The action escrow is refilled before it can wedge a player
- Found on devnet: a two-card `claim_all` with 2,004,160 lamports in the action escrow could pay both receipts but would have left the escrow below rent. That is a transaction-level error (`InsufficientFundsForRent`), not an instruction error, so the committor did not strip the actions and retry: the commit was lost. No later commit of that Player landed, `undelegate_player` is refused while claims are in flight, and the keeper cannot pay what Solana has not seen. Reproduced on a throwaway player; topping up afterwards and claiming again did not recover it.
- Decision: the client refills the escrow to 0.05 SOL whenever it is under 0.03 SOL, before `claim_all` (one wallet-signed base transaction). No program change.
- Not fixed: players already wedged stay wedged (use a new wallet on devnet). Report to MagicBlock.

## 2026-11-27: Vercel deploy as two services and one daemon
- `vercel.json` (repo root): `web` (Next.js, public at `/`), `keeper` (container, HTTP only, public at `/keeper/*`), and the `keeper-worker` daemon (same image: price relay, payout repair, inventory, sell quotes). No bindings: only the browser and the phone call the keeper.
- The loops cannot live in a service: container services scale down after 5 minutes without traffic and may run several instances. Daemons stay up but take no inbound traffic and run for production only. Services and Daemons are both in beta.
- The Dockerfile moved to `Dockerfile.keeper` at the root so the build context is the whole workspace. `--web` starts the HTTP side only. Fly config still works.
- Project env: `NEXT_PUBLIC_PRIVY_APP_ID`, `NEXT_PUBLIC_BACKEND=chain`, `KEEPER_KEYPAIR_JSON`, `FAUCET_AUTHORITY_KEYPAIR_JSON`, `PYTH_PRO_TOKEN`, `PRICE_SOURCE=pythpro`, `KEEPER_HOLD_FEEDS=mTSLA,mNVDA`, `REFILL_STOCK=1`. Leave `PORT` and `NEXT_PUBLIC_KEEPER_URL` unset. Mobile builds use `EXPO_PUBLIC_KEEPER_URL=https://<domain>/keeper`.
- Limits: faucet throttles are in memory, so on Vercel they are per instance and reset on scale-down (the 1 SOL floor still applies). Env vars are project-wide, so the web service also receives the keeper keys. Run one keeper only: stop local and Fly keepers.
- Hobby daemons get 420 GB-hours a month, about 17 days of one 1 GiB instance.
